# N27 各平台的邊界情況

使用者或其他程式做了「正常播放以外」的事時，Daphne（與 MIKU 外殼）在各平台上的行為。設計與實作細節在 N4（播放整合）、N24（輸出 API）；這裡只記「發生什麼事」。

「依據」欄：**實測**＝在實機上量過或看過；**程式**＝從程式碼判斷，還沒在實機上確認；**未驗證**＝還不知道。之後實測過的項目請改成「實測」並寫上日期或對應的文件。

## 所有平台（播放核心）

| 情境 | 行為 | 依據 |
|---|---|---|
| 有升頻濾波器時開始播放、跳轉、重開裝置 | 開頭丟掉濾波器的延遲，第一個聽到的就是音樂；結尾送零到最後一個樣本播出為止，之後的餘振不播。輸出長度等於原曲 × 倍率（N26「只播放音樂，不播濾波器延遲」） | 實測（2026-10-16，Windows 測試、Mac CLI 1M taps） |
| 跳轉 | 鏈先清空：跳轉點之後約半個濾波器長度的輸出只用到跳轉點之後的樣本（濾波器前面的歷史是零）。大 taps 下若聽到喀聲，可加短淡入（N26 待觀察） | 程式 |
| 無縫播放，下一首取樣率不同 | 只有輸出取樣率相同（例如都升到同一個取樣率）才無縫接上；否則這一首結束，由主程式載入下一首 | 程式（N4） |
| 裝置拒絕要求的取樣率 / DSD 傳輸 | 依序降級（PCM：取樣率減半；DSD：原生 → DoP → 較低倍率），每次中間的失敗都寫進 log：「the output at … failed (原因): trying …」 | 實測（假裝置的單元測試） |
| 播放中改設定（apply）後立刻 stop | stop 要等那次重開先把排隊的聲音放完、淡出，再關裝置；Mac 上一般 stop 0.84 s，這種情況約 1.7 s。結果正確 | 實測（2026-10-16，Mac + USB DAC） |
| 播放中拔除裝置 | 輸出回報失敗（`failed`），播放器停止並送 `failed` 事件，主程式決定接下來怎麼做 | 程式；實機未驗證（要有人在機器旁拔線） |

## Windows（WASAPI 獨佔 / 共享、ASIO）

| 情境 | 行為 | 依據 |
|---|---|---|
| MIKU（Daphne）以 WASAPI 獨佔播放並**暫停**，再到 Windows 音訊設定把同一台 DAC 設成預設輸出、用瀏覽器播 YouTube | 暫停不放掉裝置：WASAPI 獨佔串流照常運轉、送靜音（按播放可立刻續播）。瀏覽器走共享模式，裝置被獨佔時 Windows 拒絕它（裝置使用中），YouTube 通常會沒有聲音或音訊卡住（依瀏覽器而定）；MIKU 不受影響。MIKU 停止或結束後裝置才放出來，瀏覽器可能要暫停再播放、或重新整理頁面才恢復聲音。Windows 版 MIKU 與 Daphne 的 Windows 擴充都沒有「讓出裝置」的規則（Mac 版有，見下） | 程式；實機未驗證 |
| Windows「優先使用獨佔模式應用程式」 | 只決定獨佔程式能不能搶走正在使用的裝置；共享模式的程式不能反過來搶獨佔中的裝置 | 程式（Windows 的設計） |
| 換曲（下一首不能無縫接上） | 關閉再重開輸出。WASAPI 獨佔與 ASIO 關閉時不還原任何設定，重開時直接用新格式：只有重開那一下，沒有 Mac 那種兩次重新鎖定，也不搬系統輸出。沒有保留裝置的機制（N24「保留裝置」只做 macOS） | 程式 |
| 播放中改 Windows 的預設輸出裝置 | Daphne 的輸出不監聽預設裝置改變，繼續在原本開啟的裝置上播放；要不要搬到新裝置由主程式決定 | 程式 |
| WASAPI 裝置失效（拔除、停用、格式被改） | 輸出回報失敗（「Exclusive / Shared Device Invalidated」），見上「播放中拔除裝置」 | 程式 |
| ASIO 驅動要求重設（取樣率被改、驅動重設） | 播放器在原位置重開裝置 | 程式（N24） |
| WASAPI 共享模式 | 不是 bit-perfect，回報原因「shared mode (system mixer)」；取樣率與裝置不同時由 Windows 轉換（`AUTOCONVERTPCM`） | 實測（N24、N26） |

## macOS（Core Audio 獨佔 = hog mode / 共享）

| 情境 | 行為 | 依據 |
|---|---|---|
| 獨佔播放時的「系統輸出」 | Daphne 佔住 DAC 時，macOS 把系統輸出移到另一台裝置（例如內建輸出；只有一台裝置時就沒有系統輸出），放掉後 1–3 s 才移回。聲音照常送到 DAC。系統的其他聲音（通知等）這段時間從另一台裝置出聲 | 實測（2026-10-15，USB DAC） |
| 停止後馬上查詢系統輸出（外殼的 `probeDevice(null)`） | 頭 1–3 s 讀到的是內建輸出（上一項的副作用）；只影響顯示，停止後馬上播下一首仍送到 DAC（core 記得剛放掉的裝置）。暫緩處理（N26） | 實測 |
| 換曲（同一台裝置、獨佔，經 helper / MIKU） | 裝置保留著（hog、取樣率、DAC 格式，送靜音），下一首直接接手：同取樣率完全不動（96 k 接 96 k 換曲 30 ms），不同取樣率只重新鎖定一次；系統輸出不會移走再移回。CLI 不保留：96 k 接 96 k 要還原 44.1 kHz 再設回 96 kHz，約 1.7 s | 實測（2026-10-16，USB DAC） |
| 播完最後一首、或 MIKU 暫停 / 停止（獨佔） | 裝置保留著，其他程式不能用這台 DAC。何時放開由 MIKU 決定：MIKU 不在前景且沒在播放時約 4 s 後、改播 YouTube、或結束程式，才還原取樣率與 DAC 格式並放掉 hog | 實測（保留與放開）；放開的時機依 MIKU 的程式（`main.js`） |
| helper 程序當掉（保留著裝置時） | 系統跟著程序放掉 hog，但 DAC 的取樣率停在最後的值，不會還原（與 MIKU 自己的輸出相同）。外殼會重新啟動 helper 並從原位置繼續（一分鐘最多 3 次） | 程式 |
| 其他程式改 DAC 的取樣率（例如「音訊 MIDI 設定」） | 獨佔：macOS 拒絕其他程序的變更（`'!hog'`），照常 bit-perfect 播完。共享：在原位置以新的取樣率重開，播到結尾 | 實測（2026-10-15） |
| 裝置被其他程序 hog 住 | 獨佔與共享都開不了，回報「… is in exclusive use by another application (pid N)」，不會卡住 | 實測（N24） |
| 共享模式，裝置取樣率不是要求值的整數倍（48 k 檔、44.1 kHz 的裝置） | 由 Core Audio 的 `AudioConverter` 在 IO 回呼裡轉換（與 WASAPI 共享相同）；整數倍時由 Daphne 自己的升頻濾波器做 | 實測（2026-10-15） |
| DSD | macOS 沒有原生 DSD API，只走 DoP（獨佔）；共享模式轉成 PCM。DAC 宣稱的最高倍率不一定可靠（測試用的 USB DAC 只到 DSD128） | 實測 |
| Mac 進入閒置睡眠（例如從 ssh 操作、沒有人登入） | dark wake 時任何裝置都沒有音訊 IO（回呼數為 0），播放會卡住。測試機已設定永不睡眠（`pmset -a sleep 0`） | 實測（2026-10-16） |
| 錄音（例如錄 BlackHole 驗證 bit-perfect）的程序沒有麥克風權限 | macOS 10.14 起錄任何輸入裝置都要麥克風權限；沒有權限時不會報錯，只會收到全零。從 ssh 執行的程序沒有這個權限，要在圖形介面的終端機授權一次 | 實測（2026-10-16） |
| hog 住、停止中的裝置被改取樣率後再放掉 hog | 這個程序之後無法在它上面開始 IO（`AudioDeviceStart` 卡住數秒，MIKU 遇過）。所以 Daphne 只在 IO 運轉中改取樣率與格式（N24） | 程式（MIKU 的經驗） |

## Linux

| 情境 | 行為 | 依據 |
|---|---|---|
| 輸出 | ALSA 輸出還沒做（N26 暫緩），目前 Linux 版只有解碼、DSP 與測試，沒有實體裝置輸出 | 程式 |
| 即時排程 | 處理執行緒拿到 `SCHED_FIFO` 時，它建立的執行緒會回到 `SCHED_OTHER`（N26 尚未驗證） | 未驗證 |
