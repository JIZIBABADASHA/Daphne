# N25 跨平台

`platform/`、`core/include/daphne/engine/player.h`（`PlayerDeps`）、`core/src/output_win.cpp`、`core/src/output_none.cpp`、`tests/fake_output.h`、`tests/test_player.cpp`、`.github/workflows/build.yml`

引擎、處理鏈與播放器是一般的 C++20；作業系統相關的部分集中在 `platform/` 與裝置輸出。Windows、macOS、Linux 都能建置並執行全部單元測試。目前只有 Windows 有實際的裝置輸出（WASAPI / ASIO）；macOS（Core Audio）與 Linux（ALSA）是後續步驟（見文末）。

## 分層

```
host（MIKU 擴充 / CLI）
   │  C API（dc_*）
Player ── DspChain、解碼器、DSD 封裝（可攜）
   │  PlayerDeps：裝置輸出、PCM 解碼器
   ├── 裝置輸出（AudioOutput）：Windows：WASAPI、ASIO｜測試：FakeOutput
   └── platform/：執行緒排程、浮點控制、環境變數、快取資料夾、開檔
```

依賴只往下走：播放器不知道自己在哪個作業系統上，也不知道裝置是哪一種。

## platform 層（`daphne_platform`）

| 項目 | Windows | macOS | Linux |
|---|---|---|---|
| `RealtimeScope`（處理執行緒） | MMCSS「Audio」、1 ms 計時器解析度、關閉 EcoQoS 節流（與先前相同） | time-constraint policy（每 10 ms 最多 5 ms） | `SCHED_FIFO`（範圍下三分之一；沒有權限時維持原狀） |
| `RealtimeHelperScope`（調變器右聲道） | MMCSS「Audio」 | 同上 | 同上 |
| 執行緒優先權（背景 / 低於一般 / 一般 / 高於一般） | `THREAD_MODE_BACKGROUND_BEGIN` 與對應的 `THREAD_PRIORITY_*` | QoS：background / utility / default / user-initiated | `SCHED_IDLE`；其他為 `SCHED_OTHER` 加 nice（5 / 0 / −5） |
| FTZ / DAZ | MXCSR（x86） | FPCR.FZ（Apple Silicon）；MXCSR（Intel） | MXCSR 或 FPCR |
| 使用者快取資料夾 | `%LOCALAPPDATA%` | `~/Library/Caches` | `$XDG_CACHE_HOME`，否則 `~/.cache` |
| 開檔、64 位元 seek | `_wfopen_s`、`_fseeki64` | `fopen`、`fseeko` | 同 macOS |

- 排程是盡力而為：作業系統拒絕時執行緒維持原狀，不會失敗（`RealtimeScope::realtime()` 回報是否成功）。
- 濾波器快取：`<使用者快取>/daphne/filters`，`DAPHNE_FILTER_CACHE` 在三個平台都照舊可用。
- `parallel_for` 的 worker 沿用建立者的優先權：Windows 讀實際值，其他平台記錄在 thread_local（只有經由這一層設定的值）。

## 路徑

- 引擎一律用 `std::filesystem::path`（`Decoder::open`、`open_decoder`、`DsdFile`、`Player`、`filter_cache_dir`）。Windows 上是原生 UTF-16，其他平台是 UTF-8。
- 副檔名判斷統一用 `file_extension()`（最後一個 `.` 之後、ASCII 小寫），取代原本兩份相同的程式碼。
- dr_wav / dr_flac / minimp3 在 Windows 用 `_w` 版本，其他平台用 `char` 版本；FFmpeg 收 UTF-8。

## 裝置輸出

- `Player` 從 `PlayerDeps` 取得裝置（`OutputOpener`）與 PCM 解碼器（`DecoderOpener`）；沒給時用 `platform_output_opener()` 與 `open_decoder`。
  - `output_win.cpp`：WASAPI 獨占 / 共享、ASIO，建立方式與先前相同。
  - `output_none.cpp`（macOS / Linux）：目前沒有裝置，開啟時回報原因；裝置列表為空。
- 原本對 `AsioOutput` / `WasapiOutput` 的 `dynamic_cast` 改成 `AudioOutput` 的虛擬函式（N24）：`probe_before_design()`、`supported_rates()`、`buffer_fallback()`。
- 開啟裝置之前就要決定的事，依輸出 API 判斷（`player.cpp`）：有沒有原生 DSD（ASIO）、是不是共享混音（WASAPI 共享，不能送 DSD）、緩衝長度由播放器設定（WASAPI）。

## dsp

- AVX2 的 double-double 核心只在 x86 建置（`DAPHNE_DD_AVX2`）；其他 CPU（Apple Silicon、ARM64 Linux）走 scalar 路徑，運算順序相同，結果逐位元相同（N8）。
- GCC / Clang 現在也以 `__builtin_cpu_supports` 偵測 AVX2 + FMA，先前只有 MSVC 會用到 AVX2 路徑。

## C API（決定紀錄）

- 原本收 `wchar_t*` 路徑的函式全部保留，行為不變，MIKU 的 C# 擴充不用改。
- 新增 UTF-8 版本：`dc_load_utf8`、`dc_set_next_utf8`、`dc_set_next_gain_utf8`、`dc_filter_cache_dir_utf8`。新的 host（macOS、Linux）建議用這些。
- `dc_abi_version()` 由 1 改為 2（只有新增）。
- 其他平台的 `wchar_t` 是 UTF-32：`wchar_t` 版本在那裡仍可用，內部轉成 UTF-8。
- 共享庫只匯出 `dc_*`（`daphne_core.dll` / `libdaphne_core.so` / `libdaphne_core.dylib`）。

## CLI

- 參數一律是 UTF-8：Windows 的 `wmain` 先把 UTF-16 轉成 UTF-8，其他平台直接用 `main`；路徑在交給引擎或開檔時才轉成 `std::filesystem::path`。
- `decode-test --md5` 改用內建的 MD5（RFC 1321），不再依賴 BCrypt。
- Ctrl+C：Windows 用 console handler，其他平台用 `SIGINT` / `SIGTERM`。

## 建置

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --config Release --parallel
ctest --test-dir build -C Release --output-on-failure
```

- Windows 照舊可用 `scripts\build.cmd`。
- 靜態庫一律編成 position-independent，才能放進共享的 `daphne_core`；符號預設隱藏。
- FFmpeg：Windows 用 `third_party/ffmpeg`（`scripts/fetch_ffmpeg.ps1`）；macOS / Linux 有安裝開發套件時用 pkg-config 找到。
- ASIO SDK 只在 Windows 使用。
- MSVC 專用的 `#pragma warning` 只在 MSVC 生效。
- CI（`.github/workflows/build.yml`）：Windows（MSVC）、Linux（GCC）、macOS 14（Apple Silicon、Clang），每個 PR 都建置並跑全部單元測試。

## 播放器測試（`tests/test_player.cpp`）

`FakeOutput` 經由與 WASAPI / ASIO 相同的 `RingFeeder` 讀環。每次先等到有一整個緩衝的資料（最多 200 ms）才取，所以全速執行也不會 underrun，收到的就是播放器寫出的每一個樣本。來源由 `MemoryDecoder` 提供合成訊號。

| 測試 | 檢查 |
|---|---|
| 原取樣率、24-bit | bit-perfect：每個樣本與來源相同，之後全為 0；報告為 bit-perfect、沒有處理級 |
| `2x`、`auto` 升頻 | 裝置取樣率 88.2 / 705.6 kHz；長度 = 來源 × 倍率（加濾波器尾巴）；1 kHz 正弦量得 1000 ± 0.5 Hz |
| 裝置拒絕取樣率 | 依序嘗試 705.6k → 352.8k → 176.4k，以 176.4 kHz 播放，頻率正確 |
| 同取樣率無縫 | 兩軌接起來逐樣本相同，換軌回報一次 |
| 不同取樣率無縫（固定 176.4 kHz 輸出） | 經新的處理鏈接起來，裝置只開一次，接點沒有空白，第二軌頻率正確 |
| 搜尋 | 淡入之後從目標 frame 起逐樣本相同，直到結尾 |
| 暫停 | 暫停中位置不動；繼續後結尾逐樣本相同 |
| 音量 | 就地套用，裝置不重開，之後的振幅為一半 |
| 換濾波器 | 背景重建並交叉淡化，裝置不重開，長度不變、沒有空白 |
| 換輸出取樣率 | 裝置重開（44.1 → 88.2 kHz），兩段合起來涵蓋整軌一次；重開前最後一個 chunk（4096 個來源 frame：20 ms 淡出，之後為 0）在重開後從頭再播一次 |
| 驅動要求重設 | 裝置重開並從原位置繼續 |
| 即時輸入 | 預填與 0.3 s 抖動緩衝的靜音之後，是生產端的 1 kHz 正弦、沒有空白 |
| DSF 直送（DoP） | DoP 標記從前導靜音到結尾不間斷交替，音樂 frame 數正確 |
| dsd 核心（DoP） | 標記不間斷交替，長度正確 |

- `DAPHNE_PLAYER_DUMP=<資料夾>`：與時間無關的 8 個測試把裝置收到的位元組寫成 `<名稱>.bin`。重構前後各跑一次、逐位元組比較，就能確認行為沒有改變。
- 時間相關的測試（搜尋、暫停、設定變更、即時輸入）讓裝置以 4 倍速（即時輸入為 1 倍速）消耗；音軌長度足以讓背景工作在慢機器上完成。

## 播放器的結構（`core/src/player/`）

`core/src/player.cpp`（約 1800 行）拆成擁有自己狀態的元件，以及依主題分檔實作的處理執行緒：

| 檔案 | 內容 |
|---|---|
| `player.cpp` | 公開 API（`player.h`），只轉給處理執行緒 |
| `common.h` / `.cpp` | 處理區塊大小、輸出 API 的能力、`requested_rate`、`same_output`、`chain_settings`、濾波器描述、交叉淡化用的 FIFO |
| `report.h` / `.cpp`（`Report`） | 給主程式的報告與回呼、事件、設計進度、bit-perfect 與原因、濾波器描述、除錯 JSON、ASIO 取樣率 |
| `timeline.h`（`Timeline`、`Switch`） | 裝置 frame 時間軸、已解碼未聽到的無縫換軌、正在聽的軌與位置 |
| `output_session.h` / `.cpp`（`OutputSession`） | 裝置、環、正在推送的 chunk、裝置維護（驅動訊息、回呼速率、遲到的回呼、重設要求：回傳 Ok / Reopen / Fail，由播放器重開） |
| `change_plan.h` / `.cpp` | 設定變更要不要重開裝置（純函式） |
| `crossfader.h` / `.cpp`（`Crossfader`、`History`、`FadeQuantizer`） | 重建的處理鏈預熱、依內容延遲對齊、升餘弦交叉淡化；預熱用的輸入歷史；淡化後的 TPDF 重新量化 |
| `track_queue.h` / `.cpp`（`TrackQueue`） | 主程式設定的下一軌（有自己的鎖）、背景預備（開檔、需要時建新鏈）、邊界時交接 |
| `core.h`（`Player::Impl`） | 處理執行緒的狀態與方法宣告；`Stream` 介面：PCM 與 DSD 直送的差異 |
| `core.cpp` | 執行緒：開始、**單一**播放迴圈（PCM 與 DSD 直送原本各一份，現在經 `Stream` 共用）、傳輸、裝置維護、結束 |
| `pcm_stream.cpp` | PCM：開裝置與處理鏈、產生 chunk、交叉淡化到重建的處理鏈 |
| `dsd_stream.cpp` | DSD 檔直送、DSD 靜音與串流結尾 |
| `gapless.cpp` | 下一軌：預備、換解碼器、經新的處理鏈接起來、它的增益 |
| `changes.cpp` | 設定變更：就地、背景重建、重開裝置 |

## 約定與後續事項

- 重構過程中發現的 bug 另外 commit，不和搬移程式碼的 commit 混在一起。
- 處理執行緒的 sleep 輪詢（環滿時 2 ms、排空時 5 ms、等待裝置的迴圈）這次不動，之後再改成事件等待。
- 其他已知、這次不處理的事項：
  - 即時輸入的延遲：兩層緩衝（MIKU 環 0.3 s + 播放器環 0.5 s）。
  - 處理速度低於即時時沒有偵測或警告（double-double + 長濾波器在較慢的 CPU 上會持續 underrun）。
  - 不同取樣率無縫換軌與交叉淡化的預熱在處理執行緒上同步執行，長濾波器時可能超過環的 0.5 s。

## 驗證

| 項目 | 結果 |
|---|---|
| Linux GCC 13、Clang（`-Wall -Wextra`） | 建置沒有警告；全部單元測試通過（74 個測試案例） |
| 播放器測試連續 15 次、4 份同時執行 12 次 | 全部通過 |
| AddressSanitizer + UBSan | 沒有錯誤 |
| ThreadSanitizer | 只標記即時輸入的共用環（依設計以寫入位置 + fence 發布，N2）；播放器本身沒有資料競爭 |
| golden 比對：同一份程式執行兩次 | 8 個檔案逐位元組相同 |
| `decode-test --md5` | 與 Python hashlib 計算的 s32le MD5 相同 |
| Windows、macOS | 由 CI 建置與測試；實機輸出仍以 `verify/live.py` 確認 |
