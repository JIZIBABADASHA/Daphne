# N4 播放整合

`core/include/daphne/engine/chain.h`、`core/src/chain.cpp`、`core/include/daphne/engine/player.h`、`core/src/player.cpp`、`core/src/player/`（結構見 N25）、`capi/`、`cli/main.cpp`

## 處理鏈（`DspChain`）

```
解碼 → 降混（來源聲道 ≠ 裝置聲道）
     → 增益（音量 + headroom）→ 交叉饋送 → EQ          全部在原取樣率
     → pcm 核心：重取樣到裝置取樣率（原取樣率且不 apodize 時不放這一級）
       dsd 核心：同一個濾波器升到 705.6 / 768 kHz → 調變器前限幅；鏈以 PCM 結束，播放器的 DsdEncoder 調變
     → DSD 檔轉 PCM：前瞻限幅（output.dsd_pcm_limiter）
     → pcm 核心、整數裝置：TPDF 量化到裝置字長；處理鏈透明、整數來源放得進裝置時省略（bit-perfect）
```

- 裝置格式（取樣率、聲道、樣本型態）在建鏈之前決定；dsd 核心的「裝置格式」是調變器的 PCM 輸入（float64）。
- `update(s)`：只有增益、交叉饋送、EQ 改變時就地套用（增益漸變、EQ 滑動或交叉淡化）；濾波器、核心、輸出或最終量化級改變時回傳 false，需要新的鏈。
- `content_delay()`：重取樣器核心峰值位置 + 各級延遲，用來對齊兩條鏈的交叉淡化與無縫換軌。各級以 `Block::content_delay_frames()` 回報（預設是 `latency_frames()`；重取樣器不插入區塊延遲、`latency_frames()` 為 0（N6），改回報核心峰值位置）。
- 各級之間的緩衝區大小取自 `output_format().max_frames`（這一級最多輸出的 frames），處理鏈不需要知道哪一級會改變 frame 數。
- `flush()` 的暫存緩衝區預先配置，不在串流結束時配置記憶體。

## 播放器（`Player`）

一條處理執行緒（`platform::RealtimeScope`：Windows 為 MMCSS「Audio」、1 ms 計時器解析度、關閉 EcoQoS 節流；macOS / Linux 見 N25；都有 FTZ / DAZ）負責解碼、處理、轉換並寫入環形緩衝（N23），裝置回呼只從環裡讀。

裝置與 PCM 解碼器由 `PlayerDeps` 提供（預設為這個平台的輸出與 `open_decoder`；測試給假裝置與合成來源，N25）。播放器只透過 `AudioOutput` 介面使用裝置（N24）。

### 開始

- pcm 核心：要求 `pcm_output_rate`；裝置打不開或開始不了時，以 2 的冪逐次降低取樣率重試（仍須是來源的整數倍）。
- dsd 核心：ASIO 先試原生 DSD、再試 DoP；裝置拒絕的 DSD 倍率逐次降到 DSD64；`output.max_dsd` 限制起點。WASAPI 共享模式無法傳 DSD，直接報錯。
- ASIO：先短暫啟動一次確認驅動真的能串流這個取樣率，才開始設計濾波器。
- 需要設計的濾波器先查快取；沒有時發出「正在設計」事件並回報進度。
- 預填環形緩衝後才啟動裝置；DSD 先送 `output.dsd_lead_in_ms` 的靜音。
- 報告：來源、裝置格式、bit-perfect 與否及原因、濾波器描述、作用中的處理級。

### DSD 檔

- 裝置能接受 DSD（ASIO 原生或 DoP）時直送，不經任何處理；否則轉成 PCM（N3）走 PCM 路徑。
- 共享模式下轉成混音器取樣率（能整除 DSD 取樣率時）。

### 播放中改設定（`apply`）

| 類型 | 條件 | 做法 |
|---|---|---|
| 就地 | 只有增益 / 交叉饋送 / EQ / headroom 改變 | `DspChain::update`，無縫 |
| 重建 | 濾波器或最終量化級改變 | 新鏈在背景執行緒建立（低於正常優先權，可被更新的設定取消），以最近的輸入預熱（也在背景，見下），依內容延遲對齊，50 ms 升餘弦交叉淡化 |
| 重開裝置 | 核心、輸出取樣率、輸出裝置、調變器設定改變 | 播完已排隊的部分、最後一塊淡出、裝置排空後重開，在目前位置繼續並淡入 |

重建的預熱（最近約 3 秒的輸入通過新鏈）不在處理執行緒上做：長濾波器時它可能比環還長。

- 背景執行緒（低於正常優先權，與處理執行緒相同的 flush-to-zero）以輸入歷史預熱新鏈，目前的處理鏈照常播放。
- 一輪結束時，這段時間解碼的輸入再交給下一輪。只要每一輪比上一輪短（背景比輸入快）就繼續，最多 4 輪。
- 剩下不到一個區塊（4096 frames）時由處理執行緒補完，交叉淡化開始。若輪次不再縮短（處理鏈比輸入慢），也由處理執行緒補完，最多是上一輪的量。
- 若歷史已經不含需要的輸入（高取樣率下一輪太久），就在處理執行緒上從頭預熱，與之前相同。
- 從同一段歷史開始時，分輪預熱與一次預熱的結果逐位元組相同：同一條鏈依序收到相同的輸入，對齊點依開始交叉淡化時目前鏈的位置計算（`tests/test_player.cpp`）。預熱從第一輪開始時的歷史算起，所以新鏈比一次預熱多看到幾輪的輸入，對齊與內容不變。
- 預熱期間的搜尋讓新鏈直接接手（與交叉淡化中搜尋相同）；重開裝置或播放結束則捨棄它。這三種情形都先取消背景的這一輪（`Warm::cancel`，下一個區塊就停），不等它跑完：長濾波器在慢機器上一輪可能要好幾秒，停止或搜尋會卡那麼久。被取消的鏈搜尋時會先 `reset()` 再接手。
- 背景工作（預熱、背景重建）在 `PoolThreadScope` 裡執行，結束時還原浮點控制與一般優先權：MSVC 的 `std::async` 在執行緒池上執行並重複使用執行緒，否則下一個工作（例如濾波器設計）會繼承低於正常的優先權與 flush-to-zero。

同一時間只處理一個變更；處理中的新變更排隊，最新的一個生效。

### 傳輸

- 暫停：裝置繼續運轉（N23），PCM 淡出，DSD 送靜音。
- 搜尋：裝置暫停、清空環（裝置運轉中也安全，N23）、重新預填、繼續。
- 即時輸入（N2）暫停後繼續時會搜尋目前位置：來源暫停期間也一直寫入，解碼器跳回寫入端後方，略過那段積壓（事件「live input: back to the writer」）。即時輸入的環只填到 2 個裝置緩衝（N23），每次讀 10 ms。
- 交叉淡化、淡入、淡出在處理鏈之後改變位準：整數裝置上這些樣本以 TPDF 抖動重新量化到裝置字長（N21）。

### 無縫播放（`set_next`）

- 下一軌在背景執行緒提前開啟；若取樣率不同但能在同一個輸出上播放，連新的處理鏈也提前建好，邊界不用等慢速磁碟或濾波器設計。
- 同取樣率、目前的處理鏈也適用（`DspChain::fits`）：解碼器在邊界直接換成下一軌。
  - 處理鏈依來源而定的部分：取樣率、聲道數、降混時的聲道配置、是否 DSD 轉 PCM，以及要不要最終量化（N21：整數來源放得進裝置字長、且處理鏈透明時才省略）。
  - 所以同取樣率也可能需要新的處理鏈：例如 16-bit 裝置上 16-bit 曲目（bit-perfect，沒有量化級）之後接 24-bit 曲目，需要 TPDF 量化；無損曲目之後接有損曲目也一樣。這時與不同取樣率相同，用提前建好的新鏈接起來。
- 不同取樣率、同一輸出（例如 `output.rate` 為固定值或 `auto`），或同取樣率但需要新的處理鏈：當作一個濾波器接起來。
  - 舊鏈送入 0，帶出前一軌最後的樣本與振鈴。
  - 新鏈處理下一軌開頭，疊加在上面，使下一軌第一個樣本剛好落在前一軌最後一個樣本之後一個來源週期。
  - 新鏈的開頭要涵蓋舊鏈整段尾巴（約兩倍的內容延遲），之後新鏈的輸出才接在後面。以前只處理到新鏈的第一個樣本出來為止：濾波器長時（8192 taps、44.1 → 176.4 kHz），尾巴比這段長約 12500 frames，下一軌在那裡停頓、之後晚這麼多才繼續。
  - 這段接合由處理執行緒一次做一個區塊（`Join`，`join_produce`）：舊鏈的 0 與 flush、新鏈的讀取都只做到下一塊輸出需要的量，與一般播放相同的節奏。以前在邊界一次算完，長濾波器時可能超過環的 0.5 s。輸出與一次算完的相同（`gapless_cross` 的 dump 逐位元組相同）。
  - 接合中不接受新的設定變更與另一個這樣的接合；搜尋或重開裝置時捨棄它。舊鏈在接合聽到之後仍由接合持有，直到它的尾巴做完。
- 每一軌的 headroom（ReplayGain）在它第一個樣本被解碼的位置生效（增益 20 ms 漸變），不是在主程式收到換軌通知時。
- 新的處理鏈在邊界還沒建好（或設定已改變）時不做無縫，這一軌結束，由主程式載入下一軌。
- 換軌在實際聽到時才回報（`on_track_started`）；聽到之前若搜尋或重開裝置，回到原本那一軌與它的增益。
- 報告的 `bit_perfect` 與原因在每次換軌被聽到、就地套用設定、新鏈接手時重新計算（依聽到的那一軌與它的處理鏈），不只在開始時。

### 裝置維護

- 驅動訊息、回呼過快（驅動在背後改了緩衝大小）、遲到的回呼都寫進事件記錄。
- 驅動要求重設時重開裝置並在原位置繼續，10 秒內最多 3 次。
- DoP 串流在停止前補 PCM 靜音，DAC 離開 DSD 模式。

### 處理速度（`realtime_factor`）

- 處理執行緒量測處理鏈與其後的轉換（漸變、裝置格式轉換、DoP / DSD 封裝）花的時間，不含讀檔、等待裝置與無縫換軌的預備；每 2 秒音訊更新一次倍數（音訊秒數 ÷ 處理秒數），放在報告的 `realtime_factor`（C API 的 `report.realtime`、除錯 JSON 的 `rt`）。`dc_state` 的 `report.realtime` 每次讀取時取最新的值（`Player::realtime_factor()`），不是上次開始 / 變更時報告裡的值（那時還沒有量測，是 0）。
- 連續兩個 2 秒區段低於 1.2 倍時發出一次 `info` 事件：裝置會持續 underrun，建議改用較短的濾波器、不用 double-double 摺積或降低輸出取樣率。回到 1.5 倍以上才會再次警告，所以一段持續的慢速只有一則。
- 換處理鏈（開始、需要重開的設定變更、不同處理鏈的無縫換軌、交叉淡化結束）時重新量測：濾波器的冷啟動不算進新鏈的速度。
- 1.2 倍而不是 1 倍：環只有約 0.5 s，排程抖動與其他行程會吃掉剩下的餘裕。

## C API（`capi/daphne_core.h`，`daphne_core.dll` / `libdaphne_core.so` / `.dylib`）

呼叫只有主程式 → 函式庫一個方向；事件與狀態以 JSON（UTF-8）輪詢；錯誤以回傳碼加選用訊息緩衝區表示，例外不會越過邊界（處理執行緒與背景執行緒上的例外也轉成載入失敗或 `failed` 事件，N27）；每個函式都可以從任何執行緒呼叫。

| 函式 | 說明 |
|---|---|
| `dc_abi_version` | 2：有 `*_utf8` 函式（N25）；3：有保留裝置的函式 |
| `dc_create` / `dc_destroy` | 建立 / 停止並釋放 |
| `dc_load(path, settings_json, seconds, play)` | 開檔並開始（或暫停）；阻塞到開始或失敗。回傳 `DC_ERR_SETTINGS` / `DC_ERR_FILE` / `DC_ERR_DEVICE`。`path` 為 `wchar_t`（Windows：UTF-16）；`dc_load_utf8` 收 UTF-8 |
| `dc_apply(settings_json)` | 播放中改設定 |
| `dc_pause` / `dc_seek` / `dc_stop` | 傳輸 |
| `dc_set_next(path)` / `dc_set_next_gain(path, headroom_db)` | 無縫的下一軌（與它自己的增益；NaN 表示沿用）；`*_utf8` 版本收 UTF-8 |
| `dc_state(json)` | 狀態、位置、長度、換軌計數、設計進度、錯誤、報告、ASIO 可用取樣率 |
| `dc_poll_event(json)` | `started` / `track` / `changed` / `ended` / `failed` / `info` |
| `dc_design` / `dc_meter` | 設計進度、電平 |
| `dc_filter_cache_dir`（`_utf8`）/ `dc_filter_cache_prune` | 濾波器快取 |
| `dc_devices(json)` | 輸出裝置 |
| `dc_keep_device(on)` / `dc_release_device()` / `dc_device_kept()` | macOS 獨佔：換曲時保留裝置（整個程序；N24「保留裝置」）、放掉保留的裝置（還原後回傳 1）、目前是否保留著 |
| `dc_live_bus(base, cap_frames, rate)` / `dc_live_rate(rate)` | 即時輸入的共用環形緩衝與來源取樣率；`dc_load` 以路徑 `live:` 播放（N2） |

## helper 程序（`helper/main.cpp`，`daphne-helper`）

給不是原生程式的主程式用（macOS 的 MIKU 是 Electron）：播放器跑在子程序裡，stdin / stdout 每行一個 JSON 物件（UTF-8），底下就是上面的 C API，一個指令一次呼叫，所以主程式的行為與 Windows 擴充經 P/Invoke 呼叫時相同。子程序掛掉不會拖垮主程式；主程式結束（stdin 讀到結尾）時 helper 停止播放、放開裝置再結束。

| 請求（`{"id": n, "cmd": ...}`） | 回應（`{"id": n, "ok": ...}`） |
|---|---|
| `hello` | `version`、`abi` |
| `load`：`path`（UTF-8）、`settings`（物件或字串）、`seek`、`play` | `code`、`error`（阻塞到開始或失敗） |
| `apply`：`settings` | `code`、`error` |
| `pause`：`paused`；`seek`：`seconds`；`next`：`path`、`gain`（dB 或 null）；`stop`：`hold` | — |
| `state` | `state`（`dc_state` 的物件）、`kept`（保留著裝置、沒有載入） |
| `meter` | `l`、`r` |
| `devices` | `devices`（`dc_devices` 的物件） |
| `cache_dir`；`cache_prune`：`settings`、`limit_mb` | `dir`；`bytes` |
| `quit` | 停止播放、回應後結束 |

- 主動送出（沒有 `id`）：`{"e": "hello", ...}`（啟動時一次）、`{"e": "event", "event": {...}}`（`dc_poll_event`，每 20 ms 檢查）、`{"e": "design", "progress": x}`（濾波器設計進度改變時）。
- 指令依序在一條執行緒上執行（設計長濾波器時 `load` 可能要幾分鐘）；`state`、`meter`、`devices`、`cache_dir`、`hello` 由讀取的執行緒立刻回答，主程式的計時器不會等 `load`。`quit` 也由讀取的執行緒處理：停止讀取、丟掉還沒開始的指令、停止播放、等目前的指令結束才回應（在 Windows 上，從別的執行緒關掉 stdin 打斷不了阻塞中的讀取）。
- helper 啟動時打開 `dc_keep_device`（與 MIKU 自己的 Core Audio 輸出相同）：macOS 獨佔模式下，播完、`stop` 帶 `hold`、下一次 `load` 之前，裝置都保留著（hog、取樣率、DAC 格式，IO 送靜音），下一次 `load` 同一台裝置時直接接手。`stop` 不帶 `hold` 放開裝置（還原取樣率與 DAC 格式、放掉 hog，N24）：MIKU 播 YouTube Music、離開 MIKU 且沒在播時要的「讓出裝置」就是它；`quit` 與 stdin 結束也會放開。
- macOS MIKU 的模組（`miku/`）以 helper 實作 MIKU 的播放核心：`extension.js`（模組、頁面的 RPC：`state`、`set`、`openCache`、`clearCache`、`bitPerfect`）、`engine.js`（MIKU 的 `AudioEngine` 驅動的 backend：載入、傳輸、無縫、保留與讓出裝置（`stop({ release })`、`release()`、`holdsDevice`，與 MIKU 的 `native-audio.js` 相同）、裝置列表）、`settings-map.js`（MIKU 的設定 → Daphne 的設定）、`signal.js`（播放路徑卡片）、`helper-client.js`；頁面檔案與 Windows 擴充相同（`miku/web` 是指向 `src/Daphne.Extension/web` 的 symlink）。`verify/miku_shell.js` 以替身 host 驅動它（N26 步驟 7d）。
- 驗證：`verify/helper.py <daphne-helper> [settings]`（兩個 −60 dBFS 的短檔：暫停載入、無縫的下一軌、事件順序、stop 之後 idle 且沒有裝置被 hog、找不到檔案為 −3、未知指令、quit）。Windows（Hi-Fi Cable）與 macOS 11（內建輸出，Core Audio 獨佔）全部通過。

## CLI

```
daphne devices [--probe]
daphne play [--settings file] [--device id|index] [--shared|--exclusive|--asio [driver]]
            [--start S] [--length S] [--next file] [--watch] [--script t:cmd,...] files...
daphne render-dsp <in> <out.wav> [--settings file] [--channels N] [--bits 16|24|32] [--float]
```

- `--watch`：設定檔一改就套用（測試就地 / 重建 / 重開）。
- `--script "1.5:pause,2.5:resume,3.5:seek=1"`：依時間執行傳輸指令。
- `render-dsp`：整條處理鏈離線輸出成 WAV（虛擬裝置：`--bits` 整數位元深度，預設 24；`--float` 為 float32）；dsd 核心輸出播放器實際送出的 DoP 串流。
- 播放時的裝置位元深度不是設定項：WASAPI 獨占由寬到窄協商（int32 → 24-in-32 → float32 → packed24 → int16），ASIO 用驅動指定的樣本型態（N24）。

## 驗證

### 與重構前的實作比較（`render-dsp`，3 秒 24-bit 隨機立體聲）

| 設定 | 結果 |
|---|---|
| 原取樣率、不處理 | 逐樣本相同，且等於來源（bit-perfect） |
| auto（705.6 kHz）、24-bit | 逐樣本相同 |
| 2x、16-bit、apodize | 逐樣本相同 |
| 原取樣率、音量 −6 dB | 逐樣本相同 |
| 原取樣率、交叉饋送 | 逐樣本相同 |
